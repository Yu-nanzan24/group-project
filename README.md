# group-project

## 1. サービス概要・メンバー・実行環境

### サービス内容
クライアントから送信された文字列をサーバーで処理し、結果をクライアントに返すTCP通信プログラムである。

### メンバーと担当
- `protocol.md`：西村
- `tcp_server.c`：森岡
- `tcp_client.c`：伊藤

### 実行環境・必要な依存関係
- 実行環境：Ubuntu
- 使用言語：C言語
- 通信方式：TCP
- コンパイラ：GCC
- テスト用コマンド：`nc`（netcat）

## 2. ビルド方法

プロジェクトのルートディレクトリで、次のコマンドを実行する。

```bash
gcc -Wall -o tcp_server server/tcp_server.c
gcc -Wall -o tcp_client client/tcp_client.c
```

## 3. サーバーの起動方法

プロジェクトのルートディレクトリで、次のコマンドを実行する。

```bash
./tcp_server
```

サーバーはポート 5000 で接続を待ち受ける。

起動時には、次のように表示される。

```text
LISTEN 0.0.0.0:5000
```

クライアントが切断した後も、サーバーは次のクライアントからの接続を待ち受ける。

## 4. クライアントの起動方法

プロジェクトのルートディレクトリで、接続先のIPv4アドレスとポート番号を指定して実行する。

```bash
./tcp_client 接続先IP ポート番号
```

実行例：

```bash
./tcp_client 127.0.0.1 5000
```

クライアントの入力画面でリクエストを入力し、Enterキーを押すとサーバーに送信される。

## 5. 実装済み・未実装のリクエスト

### 実装済みリクエスト

| リクエスト | 処理内容 | 応答例 |
|---|---|---|
| UPPER hello | 小文字を大文字に変換する | OK HELLO |
| LOWER HELLO | 大文字を小文字に変換する | OK hello |
| LENGTH hello | 文字列のバイト数を返す | OK 5 |

### エラー応答

| リクエスト | 応答例 | 内容 |
|---|---|---|
| UNKNOWN hello | ERROR unknown-command | 未対応のコマンド |
| UPPER | ERROR invalid-argument | 引数が指定されていない |

### 未実装の機能
- 1024バイトを超える長いリクエストへの対応
- 複数クライアントの同時処理
- その他、`protocol.md` で定義されているが未実装のリクエスト（該当する場合）

## 6. テスト方法と実験結果

### 6.1 自作クライアントによるテスト

実行コマンド：

```bash
./tcp_client 127.0.0.1 5000
```

UPPER hello を送信し、サーバーから OK HELLO が返ることを確認した。

### 6.2 nc によるテスト

サーバーを起動した状態で、別のターミナルから次のコマンドを実行する。

```bash
nc 127.0.0.1 5000
```

確認したリクエストと応答：

| リクエスト | 期待される応答 | 確認結果 |
|---|---|---|
| UPPER hello | OK HELLO | 成功 |
| LOWER HELLO | OK hello | 成功 |
| LENGTH hello | OK 5 | 成功 |
| UNKNOWN hello | ERROR unknown-command | 成功 |
| UPPER | ERROR invalid-argument | 成功 |

また、エラーリクエストの後に正常なリクエストを送信し、同じ接続の中で正常な応答が返ることを確認した。

### 6.3 再接続テスト

1. 1人目のクライアントから UPPER hello を送信し、`OK HELLO` が返ることを確認した。
2. 1人目のクライアントを切断した。
3. サーバーが終了せず、接続待ちを続けることを確認した。
4. 2人目のクライアントから再接続し、`LENGTH hello` を送信した。
5. OK 5 が返ることを確認した。

以上から、クライアント切断後も次の接続を受け付けられることを確認した。

## 7. 現在分かっている問題・制限

- 文字列の長さは文字数ではなくバイト数として計算する。
- 実装と protocol.md の仕様が一致しているか、今後も確認する必要がある。

## 以下第７回追記分

## 複数client対応方式
- fork()を選択、子プロセスをclientごとに作成して並行処理が可能なため
## FD・プロセスの終了管理
- 親プロセスはfork後にclient用のファイルディスクリプタをcloseし、子プロセスはlisten_fdを先にcloseし、その後にclient用のファイルディスクリプタをcloseした。
- 終了した子プロセスはsignalによってゾンビプロセスが残らないよう対応した。
## 共有状態の有無
- 親プロセスと子プロセスには直接のつながりはなく、clientごとの値はそれぞれの子プロセスに格納されている。
